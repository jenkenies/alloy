# Alloy v0.3 设计文档：strict 七阶段严格全流程

日期：2026-10-20
状态：已确认（用户批准）
类型：Claude Code 插件 — v0.2 的增量演进
前置文档：[alloy-v0.2-dual-mode-design.md](2026-09-24-alloy-v0.2-dual-mode-design.md)

## 1. 定位与动机

v0.2 strict 五阶段（explore → brainstorm → spec → 实现 → 交付）上线后，用户提出两个诉求：

1. **全流程严格化**：需求分析 → 设计方案 → **plan（实施计划）** → 编码 → **自测验证**，每一环都要严格实现。现状 plan 与自测验证都不是独立阶段。
2. **模糊点必须用户确认**：v0.2 brainstorm 的"仅 4 类场景必须问、默认不打扰"与该诉求冲突。

同时用户反馈四类"卡壳"现象仍存在：①确认门禁处卡住（模型死等或用户不知回复什么）②subagent 慢/无响应 ③阶段衔接丢上下文（确认过的结论丢失、重复探索）④提问太多太碎。

根因分析：v0.2 流程靠**会话记忆**衔接、靠**措辞**约束等待行为。丢上下文与死等都是该根源的症状。v0.3 的解法：**产物落盘 + 门禁语义精确化 + 交互轮次收敛**。

## 2. 架构决策

- **方案 A：orchestrator 原位升级**（替代 B 新增独立 full skill、C 合并重写单 skill）。延续 v0.2"骨架共享 + 阶段叠加"：fast 保持四阶段极简不动，strict 升级为七阶段。理由：不新增并行流程逻辑，改动聚焦，维护成本最低（用户已确认）。
- **模糊点交互：一次性清单确认**（替代逐条一次一问、一次性自由清单）。穷举模糊点后落盘清单，每项含问题/选项/唯一推荐/依赖标注，一次性提交用户逐项裁决；优先 AskUserQuestion 选择题（每批 ≤4），用户可"全部按推荐"一键通过（用户已确认）。
- **状态持久化：全量落盘 + STATUS.md**（推翻 v0.2"不做状态持久化"决策）。产物落盘 `docs/alloy/<日期-任务slug>/`，STATUS.md 记录阶段状态；门禁续跑从文件恢复，不依赖会话记忆，支持跨会话续跑（用户已确认）。（v0.3.1 更新：目录规范改为 `docs/superpowers/` 类型分目录，见 §14）
- **门禁收敛为 3 个**：严格 ≠ 多轮打扰。7 阶段仅 3 个用户门禁；v0.2 的 `[未收敛]` 独立停靠取消，待裁决项并入门禁 2 清单一次批掉。
- **YAGNI 边界**：不做无人值守模式、不做多任务并行实现、不引入 Python bridge 门禁；纯 markdown 认知层 + 现有 doctor.js。

## 3. strict 七阶段总览与门禁分布

```
explore → brainstorm → spec → plan → implement → verify → 交付
            │门禁1        │  门禁2（spec+plan 合并确认）   │门禁3（验收）
```

| 门禁 | 位置 | 确认内容 |
|---|---|---|
| 门禁 1 | brainstorm 末 | 模糊点清单（问题/选项/推荐/依赖），一次性裁决 |
| 门禁 2 | plan 末 | 02-spec.md 摘要 + 03-plan.md 任务清单，合并确认 |
| 门禁 3 | verify 末 | 04-verify-report.md 摘要，用户验收 |

## 4. 落盘协议

任务启动时确定任务 slug：`docs/alloy/<YYYY-MM-DD>-<任务slug>/`（slug 从任务描述提取 3-6 个词，连字符连接）。

```
docs/alloy/<日期-任务slug>/
├── STATUS.md            # 阶段状态机（见 4.1）
├── 01-clarifications.md # 模糊点清单 + 用户裁决记录
├── 02-spec.md           # 设计方案（动机/方案/改动点/验收标准）
├── 03-plan.md           # 实施计划（任务清单，brief 数据源）
└── 04-verify-report.md  # 自测验证报告
```

规则：

- 每阶段产出**立即落盘**，STATUS.md 同步更新；实现阶段每任务完成即更新 STATUS.md。
- 门禁续跑从文件恢复上下文，不依赖会话记忆；已完成阶段的结论**不得重问、不得重做**（零浪费原则升级为跨会话）。
- 新会话续跑：用户说"继续 alloy 任务"→ 读 STATUS.md → 从记录阶段继续。
- openspec 可用时 spec 仍走 openspec 提案，但摘要必须同步落盘 02-spec.md（落盘是硬要求，openspec 是格式来源）。

### 4.1 STATUS.md 格式

```markdown
# Alloy 任务状态
- 任务：<一句话>
- 模式：strict
- 当前阶段：<explore|brainstorm|spec|plan|implement|verify|delivery>
- 门禁状态：<无 | 门禁N 待确认（等待内容：…） | 门禁N 已确认>
- 下一步：<用户该回复什么或系统将做什么>
- 已完成产物：<文件列表>
- 续跑指令：<从哪个阶段的哪一步继续>
```

## 5. 门禁统一协议（治"门禁处卡住"）

所有门禁执行同一硬规则：

1. 产物已落盘，STATUS.md 已更新（写明"下一步该回复什么"）。
2. 输出标准化提示：确认内容（清单/摘要）+ 可回复项：**确认 / 全部按推荐 / 指出修改点**。
3. **结束当前回合**：停止生成，不再调用任何工具，不轮询，绝不"我先继续做"。
4. 用户回复后：从 STATUS.md 记录的续跑点继续；已确认结论不重问。
5. 禁止：自问自答、替用户拍板、擅自降级跳过门禁、在门禁处输出后续阶段的产物。

门禁例外：用户明确说跳过某门禁 → 在 STATUS.md 记录"用户跳过门禁 N"，交付时注明。verify 门禁不可跳过验收本身，但报告全绿时允许用户以"通过"一词完成验收。

## 6. 阶段规格

### 阶段 0 环境探查（不变）

doctor.js 检测组件可用性，降级总表行动（见第 10 节）。

### 阶段 1 explore（不变）

codegraph MCP → CLI → Grep/Glob 降级链；rtk 前缀；超时重试 1 次即回退。探索结论要点写入 01-clarifications.md 的"探索结论"节（供后续阶段引用，防丢失）。

### 阶段 2 brainstorm（重做：穷举模糊点）

- 从 v0.2"仅 4 类必须问"改为**穷举收集**：目的 / 约束 / 成功标准 / 需求歧义 / 方案分歧 / 不可逆决策（选型、架构方向、数据结构变更），全部列出，不自行"合理决定"。
- 落盘 01-clarifications.md：每项 = 编号 + 问题 + 选项（含**唯一推荐**+理由，禁止"都可以"）+ 依赖标注（"依赖第 N 项"）。
- **门禁 1：一次性清单确认**。优先 AskUserQuestion（每批 ≤4 问，选择题）；超 4 项分批；不适合选择题的项用纯文本清单。用户可回复"全部按推荐"。
- 用户明确说跳过 → STATUS.md 记录，交付注明"brainstorm 被跳过"。
- fast 模式无本阶段（现状不变）。

### 阶段 3 spec（设计方案）

- openspec 可用 → openspec 变更提案；不可用 → 手写 02-spec.md（≤40 行：动机 / 方案 / 改动点 / **验收标准逐条可验证**）。
- ceiling 五维检查保留（完整性/自洽性/可测性/明确性/边界一致性），产出后、门禁 2 前跑。
- **[未收敛] 取消独立停靠**：五维不过 → spec 标注 `[未收敛]`，待裁决项作为条目并入 03-plan.md 前的确认清单，在门禁 2 一并让用户裁决。

### 阶段 4 plan（新增）

落盘 03-plan.md，内容：

- **任务清单**：每任务 = 编号 + 目标 + 涉及文件与符号 + 实现步骤（有序）+ 验证命令 + 依赖任务 + 规模（S/M/L：单文件机械=S，多文件=M，架构级=L）。
- **依赖关系**：标明串行链与可并行项（仅只读任务可并行）。
- **全量验证命令汇总**：implement 完成后 verify 阶段要跑的完整命令清单。
- **字段与 subagent brief 一一对应**：plan 的每任务字段直接派生 implementer brief（见 alloy-subagents），plan 阶段的严格性直接转化为 brief 质量。
- 任务 1-2 个时 plan 照常落盘（brief 字段表仍用于主会话任务组织）。

**门禁 2（spec+plan 合并确认）**：展示 02-spec.md 摘要 + 03-plan.md 任务清单 +（若有）[未收敛] 待裁决项，一次性确认。确认后 spec 与 plan 冻结，implement 阶段不再改方案（发现结构性问题 → 按 BLOCKED 升级链处理）。

### 阶段 5 implement

- 任务 1-2 个 → 主会话直接实现；≥3 个 → `alloy-subagents` 协议派发；fast 永不派发。
- brief 从 03-plan.md 派生（不再是 controller 从 spec 临时摘录）。
- TDD 纪律不变（superpowers 可用走其技能，不可用走内置轻量纪律）。
- **每任务完成即更新 STATUS.md**（已完成任务列表 + 当前任务），防断线丢进度。
- 新增防卡规则（并入 alloy-subagents）：
  1. **派发超时止损**：subagent 超过预期耗时数倍（建议 5 分钟量级）无返回 → TaskStop 终止 → 评估：任务可拆小 → 重派；不可拆 → 退回主会话直接实现该任务并注明。禁止无限等待。
  2. **implementer 提问自答优先**：implementer 返回 NEEDS_CONTEXT 时，controller 先自查（03-plan.md / 已落盘产物 / 代码库）能否自答；能 → 补齐后热续原实例；不能 → 汇总缺口一次性升级用户（不逐条挤牙膏）。
  3. v0.2 性能规则 1-6 全部保留（热续修复 / 只读审查并行 / 小任务合并审查 / diff 控体积 / 无界循环升级 / 久无返回查模型层）。

### 阶段 6 verify（新增：自测验证门禁）

强制执行（用户明确要求跳过除外，跳过须 STATUS.md 记录）：

1. **全量验证**：跑 03-plan.md 汇总的全部验证命令（编译 / 测试 / lint），记录通过/失败项数。
2. **验收逐条核对**：02-spec.md 验收标准逐条 → 通过 / 未通过 / 未覆盖，附证据（命令输出 / 文件符号）。
3. 落盘 04-verify-report.md（验证命令结果 + 验收核对表 + 遗留项）。

判定：

- 全部通过 → **门禁 3**：呈现报告摘要（≤10 行），用户验收：通过 → 交付；不通过 → 列具体问题回 implement 修复循环。
- 有未通过项 → **不等待用户**，直接回 implement 修复（仅修复失败项相关任务），修完重跑 verify；**修复循环上限 2 轮**，超限 → 带遗留项进入门禁 3，报告中明确标注遗留。

### 阶段 7 交付

caveman ≤10 行汇报（改了啥/测了啥/风险/下一步）+ strict 附派发统计 + 降级与跳过注明 + handoffs。STATUS.md 置终态（含产物索引，供后续会话查阅）。

## 8. 防卡对照表（用户四现象 → v0.3 解法）

| 现象 | 根因 | v0.3 解法 |
|---|---|---|
| 确认门禁处卡住 | "等待"无可执行语义，模型死等或用户不知回复什么 | 门禁统一协议（§5）：落盘→标准提示→结束回合→续跑 |
| subagent 慢/无响应 | 无超时止损；提问循环无解法 | 超时止损 + 提问自答优先（§6 阶段 5）；v0.2 六条性能规则保留 |
| 阶段衔接丢上下文 | 依赖会话记忆，无持久化 | 全量落盘 + STATUS.md + 从文件恢复，跨会话续跑（§4） |
| 提问太多太碎 | brainstorm 逐条问 + 门禁过多 | 一次性清单确认 + 门禁收敛 3 个 + [未收敛] 并入（§3、§6） |

## 9. 错误处理

- 继承 v0.2：组件缺失自动降级不中断；BLOCKED 升级链；降级注明。
- 新增：
  - 落盘失败（目录无写权限等）→ 退回会话内衔接并交付注明，不中断。
  - verify 修复循环 2 轮超限 → 带遗留交付（不是失败，是标注）。
  - 用户中途换会话 → 新会话读 STATUS.md 续跑；STATUS.md 丢失 → 询问用户从哪个阶段重启，禁止凭空猜测。
- fast 模式行为与 v0.2 完全一致（不含 plan/verify 独立阶段、不落盘、不派发 subagent）。

## 10. 降级总表（在 v0.2 基础上不变 + 备注）

| 组件 | 检测方式 | 不可用时 |
|---|---|---|
| codegraph | MCP 工具或 doctor ok | Grep/Glob 探索，交付注明"未建图" |
| rtk | doctor ok | 原生命令 |
| openspec | doctor ok | 手写 02-spec.md（落盘仍强制） |
| superpowers | doctor ok | 内置轻量 TDD / 内置轻量提问协议 |
| Task 工具 | 运行时可用性 | strict 退回主会话顺序实现，plan 字段表仍用于组织 |
| AskUserQuestion | 运行时可用性 | 门禁确认改纯文本清单（一次性，仍清单制） |
| caveman / ponytail | 内嵌恒可用 | 不适用 |

## 11. 测试策略

1. **命令加载冒烟**：/alloy:strict 加载后声明七阶段与 3 门禁。
2. **门禁协议**：模拟 brainstorm/plan/verify 三门禁处行为：产物落盘、STATUS 更新、标准提示、结束回合；用户"全部按推荐"可一次通过。
3. **落盘与续跑**：任一门禁处中断，新会话凭 STATUS.md 恢复且不重做已完成阶段。
4. **verify 循环**：构造测试失败 → 自动修复循环 → 2 轮超限带遗留交付且报告标注。
5. **降级**：禁 AskUserQuestion 情境下门禁退化为纯文本清单仍为一次性确认。
6. **人工验收**：真实任务完整走 strict 七阶段，对照四类卡壳现象逐项确认消除。
