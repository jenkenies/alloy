# Alloy v0.2 设计文档：双模式工作流（brainstorm + sub-agents）

日期：2026-09-24
状态：已确认（用户批准）
类型：Claude Code 插件（plugin）— v0.1 的增量演进
前置文档：[alloy-plugin-design.md](2026-09-24-alloy-plugin-design.md)

## 1. 定位与动机

v0.1 的 `/alloy:flow` 是单模式四阶段（explore → spec → 实现 → 交付），存在两个缺口：

1. **无需求澄清环节**：用户输入任务后直接探索、写 spec，需求歧义与方案分歧未对齐就落到规格里。
2. **无 sub-agents**：多任务实现全部由主会话顺序完成，上下文随任务数膨胀，审查缺失。

v0.2 引入双模式：**fast（极简，保持 v0.1 流程）** 与 **strict（严谨，新增 brainstorm 阶段 + subagent 驱动实现）**。设计参考上游实践：

- [Superpowers](https://github.com/obra/superpowers)：`subagent-driven-development`（主会话 controller + prompt 模板派发 + 双阶段审查）与 `brainstorming`（一次一问澄清）。

此外融入以下设计原则：交互决策原则（仅 4 类场景必须问）、推进深度上限 ceiling、subagent brief 字段模板、命令 handoffs 衔接。

## 2. 架构决策

- **方案 A：骨架共享 + 阶段叠加**（替代方案 B 每模式独立 skill、方案 C 单 skill 内部分支）。`alloy-orchestrator` 保持单一编排骨架声明五阶段；fast / strict 只差"是否叠加 brainstorm 阶段与 subagent 驱动"。
- **sub-agents 形态：编排协议式**（跟随 superpowers）。不定义 agents/ 目录、不写 agent 定义文件；新增 `alloy-subagents` skill（SKILL.md + 3 个 prompt 模板），主会话按模板用 Task 工具派发通用 subagent。理由：实践证明字段模板与审查协议才是质量关键，agent 定义文件只提供身份稳定性的边际收益，不符合 YAGNI。
- **不引入确定性层**：不做额外 Python bridge 门禁。v0.2 保持纯 markdown 认知层 + 现有 doctor.js，"spec 未经确认不得实现"仍靠 HARD-GATE 措辞兜底（与 v0.1 一致的诚实分层）。
- **YAGNI 边界**：不做状态持久化（state.json）、不做产物凭据链、不做无人值守裁决表、不做多轮迭代模型；本版本仅移植 ceiling 与 brief 字段模板两项进阶机制。

## 3. 命令规格

### /alloy:fast <任务描述>

极简模式，流程同 v0.1 flow：

```
explore → spec → 实现 → 交付
```

- 实现阶段：主会话直接实现，**永不派发 subagent**（避免 brief 准备成本）。
- spec 有缺口：直接列出缺口问用户，不搞 ceiling。
- 适用于：小改动、需求明确、单一任务。

### /alloy:strict <任务描述>

严谨模式，五阶段：

```
explore → brainstorm → spec → 实现 → 交付
```

- **brainstorm**（本版本新增，见第 4 节）
- **spec**：openspec 可用 → 变更提案；不可用 → `docs/specs/` 手写规格。spec 完成后跑 ceiling 检查（见第 5 节）。
- **实现**：任务 ≥3 个 → subagent 驱动（见第 6 节）；任务 1-2 个 → 主会话直接实现。
- **交付**：同 v0.1（caveman ≤10 行汇报），附 subagent 派发统计（派发数 / 审查轮次）。

### 兼容性

- `commands/flow.md` 删除（插件未发布，无兼容负担）；README 命令表同步更新。
- `/alloy:setup`、`/alloy:status` 不变。

### handoffs 衔接（命令 frontmatter）

每个工作流命令 frontmatter 增加 `description` 尾注声明下一步衔接，交付阶段末尾显式提示用户（如 strict 交付后提示"可运行 /alloy:status 查看组件统计"）。保证命令间流转可预期。

## 4. brainstorm 阶段规格（strict 独有）

位置：explore 之后、spec 之前。融合 superpowers `brainstorming` 与交互决策原则。

### 4.1 提问纪律

- 一次一问，聚焦：目的 / 约束 / 成功标准。
- **仅 4 类场景必须问**（默认不打扰）：
  1. 探索结果模糊（codegraph/搜索结果无法支撑决策）
  2. 多方案难分优劣
  3. 需求有明显歧义
  4. 涉及不可逆决策（选型、架构方向、数据结构变更）
- 能自行合理决定的**不问**；不输出 TBD/TODO 占位符。

### 4.2 方案对比

- 2-3 个候选方案，统一维度对比表：复杂度 / 性能影响 / 兼容性 / 推荐度。
- **必须给出唯一推荐**及理由，禁止"都可以"。

### 4.3 产出与跳过

- 结论（选定方案 + 澄清记录）作为 spec 提案的输入，不单独落盘文件（避免产物膨胀；结论体现在 spec 中）。
- 用户明确说"跳过"时才可跳过 brainstorm 阶段。
- superpowers brainstorming 技能可用 → 直接走该技能；不可用 → 内置轻量提问协议（即本节规则，始终可用）。

## 5. ceiling 深度上限规格（strict 的 spec 质量门禁）

spec 完成后、请求用户确认前，跑五维检查：

| 维度 | 检查内容 |
|------|----------|
| 完整性 | 动机 / 改动点 / 验收标准逐项非空 |
| 自洽性 | 文档内部无冲突（冲突时裁决规则：专门章节 > 顺带提及，后文 > 前文） |
| 可测性 | 验收标准能否导出可执行验证（测试场景/命令） |
| 明确性 | 无二义表述；歧义取"不改变现有行为"的理解 |
| 边界一致性 | 改动范围与任务描述边界交叉核对 |

### 判定

- **五维全过** → 展示 spec 摘要，等用户确认后进实现（与 v0.1 相同门禁）。
- **方案未定或存在不可判矛盾** → ceiling = explore 停靠：
  1. spec 标题标注 `[未收敛]`
  2. 产出内容改为：候选方向 + 各自 trade-off + **待裁决清单**（每项含：问题 / 选项 / 推荐项）
  3. **同会话内**停靠等用户裁决；用户裁决后从 spec 阶段续跑（不跨会话，无需持久化，与第 2 节"不做状态持久化"一致）
  4. **零浪费原则**：explore / brainstorm 已产出的上下文与结论不重做

- fast 模式不跑 ceiling（保持极简）。

## 6. subagent 编排协议规格（strict 实现阶段，任务 ≥3 时）

新增 `skills/alloy-subagents/`，结构对齐 superpowers：

```
skills/alloy-subagents/
├── SKILL.md                        # 编排协议主文档
└── prompts/
    ├── implementer-prompt.md       # 实现 brief 模板
    ├── spec-reviewer-prompt.md     # spec 合规审查模板
    └── quality-reviewer-prompt.md  # 代码质量审查模板
```

### 6.1 角色与流程

主会话 = controller；每任务派发**全新** implementer subagent（零上下文，brief 由 controller 精确构造，不继承会话历史）：

```
每任务：派 implementer（brief 全文字段，见 6.2）
  → implementer 可先提问（controller 解答后继续）
  → 实现 + TDD（测试先行）+ 自审
  → 派 spec 合规审查 subagent：✅ 通过 / ❌ 缺口 → 原 implementer 修复 → 重审
  → 派代码质量审查 subagent：✅ 通过 / ❌ 问题 → 原 implementer 修复 → 重审
  → 标记任务完成，下一任务
全部完成 → 派最终整体审查 subagent（跨任务一致性）
```

### 6.2 brief 字段模板（implementer-prompt.md 核心）

controller 为每个任务构造的 brief 必须含全字段：

| 字段 | 防的坑 |
|------|--------|
| 目标 + 场景与验收标准 | 不知道"做到什么程度" |
| 代码锚点：文件路径 + 符号名 + 锚点代码片段；**禁止裸行号** | 前置任务改动后行号漂移 |
| 前置产出契约：前置任务产出的精确符号（常量全名 / 方法签名 / DTO 字段） | 免回读前置实现 |
| 数据来源：跨链路字段的取值表达式 + 值域 + 空值处理 | 瞎猜字段来源 |
| 验证命令：编译 / 测试命令 | 无法自证完成 |
| 约束：不改无关代码 / 注释语言 / 编码规范要点 | 越界重构 |
| 卡住升级路径：连续失败 2 次 / 找不到 API 签名 / 数据来源不明 → 停止并返回状态，**禁止瞎猜** | 硬编错代码 |

### 6.3 状态上报协议

implementer 返回四态之一，controller 对应处理：

| 状态 | 处理 |
|------|------|
| DONE | 进 spec 合规审查 |
| DONE_WITH_CONCERNS | 读 concerns：正确性/范围问题先解决再审；观察性备注记录后继续 |
| NEEDS_CONTEXT | 补齐缺失上下文后重新派发 |
| BLOCKED | 依次尝试：补上下文重派 → 换更强模型重派 → 拆小任务 → 升级给用户。**禁止**无视升级或原样重试 |

### 6.4 模型分级

- 机械任务（1-2 文件、规格完整）→ 便宜快速模型
- 多文件集成 → 标准模型
- 架构判断 / 审查 → 最强模型

### 6.5 红线（Never）

- 禁止并行派发实现 subagent（会冲突；独立只读调查类才可并行）
- 禁止让 subagent 自己读 spec 文件（brief 必须带全文）
- 审查存在 open issue 不得进下一任务
- 禁止跳过任一阶段审查（spec 合规 → 质量，顺序不可颠倒）
- 禁止用 implementer 自审替代独立审查

## 8. 降级总表（新增行）

| 组件 / 能力 | 检测方式 | 不可用时 |
|---|---|---|
| superpowers brainstorming 技能 | doctor 报 ok | strict 的 brainstorm 阶段走内置轻量提问协议（第 4 节规则，始终可用） |
| Task 工具（subagent 派发） | 运行时工具可用性 | strict 实现阶段退回主会话顺序实现；brief 字段表仍用于任务组织，不浪费 |
| openspec | doctor 报 ok | `docs/specs/` 手写规格（不变，v0.1 行为） |
| codegraph / rtk / caveman / ponytail | 不变 | 不变（v0.1 降级表） |

降级原则不变：检测 → 降级 → 汇报注明，绝不中断。

## 9. 数据流

```
用户 /alloy:fast <任务>                     用户 /alloy:strict <任务>
   → fast.md 加载 alloy-orchestrator           → strict.md 加载 alloy-orchestrator
   → 四阶段，主会话顺序执行                     → explore
                                               → brainstorm（一次一问 → 唯一推荐方案）
                                               → spec（openspec/手写）→ ceiling 五维检查
                                                    ├ 全过 → 用户确认
                                                    └ 不可判 → [未收敛] 草案停靠 → 裁决 → 续跑
                                               → 实现
                                                    ├ 任务 ≤2 → 主会话直接实现
                                                    └ 任务 ≥3 → alloy-subagents 协议派发
                                               → 交付（含 subagent 统计 + handoffs 提示）
```

## 10. 错误处理

- 继承 v0.1：组件缺失自动降级不中断；setup 失败给手动兜底。
- 新增：
  - subagent BLOCKED 升级链（6.3）：补上下文 → 换模型 → 拆任务 → 升级用户，每步有出口，禁止原样重试。
  - ceiling 停靠不是失败：`[未收敛]` 草案是有效中间产物，交付时注明停靠原因与待裁决项。
  - brainstorm 被跳过：交付注明"未经 brainstorm，规格直接产出"。

## 11. 测试策略

1. **命令加载冒烟**：/plugin 安装后 `/alloy:fast`、`/alloy:strict` 均能加载 orchestrator skill 并声明正确阶段序列。
2. **降级路径**：禁用 Task 工具场景（模拟）验证 strict 退回主会话实现；隐藏 superpowers 验证轻量 brainstorm 协议生效。
3. **ceiling 路径**：构造方案未定的 spec 输入，验证产出 `[未收敛]` 草案含待裁决清单且不进入实现。
4. **subagent 协议**：小型真实仓库（≥3 任务的改动）跑通 strict 全流程，验证 brief 字段完整、双阶段审查发生、BLOCKED 升级路径可达。
5. **人工验收**：同一任务分别走 fast 与 strict，对比交付质量与 token 消耗。

## 12. 里程碑

- **v0.2（本次实施）**：双命令 + orchestrator 改造 + alloy-subagents skill（3 模板）+ README 更新。
- **v0.3（候选，暂不做）**：进阶能力按需评估——产物凭据链（防架空探索）、多轮迭代模型、无人值守裁决表。触发条件：用户反馈 spec 被架空或需要断点续跑时再评估。

## 13. 性能优化（2026-10-10 追加）

用户反馈 strict 的 subagent 模式慢且会卡住。定位 6 个根因并修复：

| # | 根因 | 修复 |
|---|---|---|
| 1 | 修复轮强制全新实例，每次重读上下文 | 修复轮热续原 implementer/reviewer 实例（SendMessage/resume agentId）；仅 agent 丢失 / 换模型 / brief 结构性错误才重派 |
| 2 | 每任务 3 个 subagent 全顺序串行 | 独立任务的 spec/质量审查（只读）可并行派发；实现 subagent 仍禁止并行 |
| 3 | NEEDS_CONTEXT / BLOCKED 无界重派 | 连续 2 次即升级用户，禁止无界循环 |
| 4 | codegraph_explore 工具存在但 MCP server 未运行 → 每次调用超时 | 超时/报错最多重试 1 次，立即回退 CLI/Grep |
| 5 | 审查 prompt 整贴大 diff，又慢又贵 | diff >~200 行改传文件清单 + 符号锚点 + 变更摘要 |
| 6 | spec 确认门禁未说明是等待输入 | 门禁处明示"等待确认是故意暂停，不是卡死" |

次要：doctor.js 探针超时 10s → 4s；小任务（单文件）合并为单审查 subagent（内部先 spec 后质量）；implementer 开工前先确认验证命令可运行，不可用立即 NEEDS_CONTEXT；subagent 久无返回先查模型层再查任务层。

涉及文件：`skills/alloy-subagents/SKILL.md`（重写）、`skills/alloy-orchestrator/SKILL.md`（3 处）、`prompts/*.md`（3 处）、`commands/strict.md`、`scripts/doctor.js`。
